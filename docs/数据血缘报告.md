## 一、概念阐释：什么是数据血缘

数据血缘（Data Lineage），又称数据谱系，是指数据在其全生命周期中**从源头到终点的完整流转路径与演化关系的可追溯记录**。它回答三个核心问题：

1. **数据从哪里来（Where from）**——数据的源头系统、原始表、上游接口是什么；
2. **数据经历了什么（What happened）**——在流转过程中经过了哪些加工、转换、聚合、过滤等处理环节；
3. **数据到哪里去（Where to）**——数据最终被哪些报表、指标、接口、应用所消费。

简言之，数据血缘就是数据的"家谱图"与"履历表"：正如血缘关系描述了人与人之间的代际传承，数据血缘描述了数据资产之间"父数据生出子数据"的派生关系。

## 二、数据血缘的核心要素

一套完整的数据血缘体系通常包含以下要素：

| 要素 | 说明 |
|:---|:---|
| 节点（Node） | 数据资产的实体单元：库表、字段、文件、API、报表、模型产物等 |
| 边（Edge） | 节点间的派生关系："A 经过变换 T 生成 B" |
| 变换（Transformation） | 边上承载的加工逻辑：SQL、ETL 作业、计算规则、模型推理等 |
| 粒度（Granularity） | 追溯精度，分为表级血缘、字段级血缘、行级血缘 |
| 方向（Direction） | 向上追溯（溯源，Backward Lineage）与向下追踪（影响分析，Forward Lineage） |

## 三、数据血缘的主要类型

1. **技术血缘**——由系统自动解析生成，如通过 SQL 解析器、ETL 元数据、调度系统日志还原出的表间依赖关系，强调客观、精确、自动化；
2. **业务血缘**——描述业务语义层面的数据来龙去脉，如"该指标由哪些业务口径的数据汇总而成"，服务于业务人员理解；
3. **操作血缘**——记录"谁在什么时间对数据做了什么操作"，偏向审计与合规视角。

## 四、数据血缘的价值

### （一）影响分析（Impact Analysis）

当上游表结构或口径变更时，可沿血缘向下追踪，快速圈定受影响的下游报表、接口与应用，避免"改一张表、崩一片报表"的盲区事故。

### （二）问题溯源（Root Cause Tracing）

当下游指标异常时，可沿血缘向上逐层回溯，定位是源头数据质量问题、中间加工逻辑缺陷，还是消费端展示错误，大幅缩短排查周期。

### （三）数据治理与合规

血缘为数据分级分类、敏感数据流转审计、监管报送（如金融行业的 EAST、1104 检查）提供证据链支撑，回答"这份数据是怎么算出来的"。

### （四）信任构建与资产沉淀

可解释的数据链路提升指标可信度，减少"同名指标多个数值"的口径纷争；血缘图本身也是组织数据资产地图，支撑资产盘点与冗余下线。

## 五、数据血缘的建设方法

1. **元数据采集**——对接数据库元数据、调度平台（Airflow / DolphinScheduler）、ETL 工具、BI 平台，统一纳入元数据中心；
2. **血缘解析**——通过 SQL 静态解析、运行时埋点（如 OpenLineage / Marquez 标准）、查询日志回放等手段提取依赖关系；
3. **存储与建模**——以图结构（Neo4j、JanusGraph 或自研图模型）存储节点与边，支持多跳遍历；
4. **可视化与应用**——提供血缘图谱 UI、影响分析 API，并嵌入变更评审、质量告警、指标管理等业务流程。

## 六、数据血缘与相关概念的关系

- **与元数据管理**：血缘是元数据的高级组织形式，元数据是"有什么数据"，血缘是"数据之间什么关系"；
- **与数据质量**：质量规则挂在血缘节点上，质量问题沿血缘传播，二者互为支撑；
- **与数据目录**：目录回答"数据在哪里、归谁管"，血缘回答"数据怎么来的、被谁用"，共同构成数据资产全景。

## 七、与 ID-009 AI 模型评测平台的关联性分析

数据血缘并非数据仓库领域的专利。ID-009 AI 模型评测平台虽为评测系统，但其核心数据流天然构成一条**典型的、端到端的数据血缘链**，具体映射如下：

### （一）评测数据流即血缘链

平台的核心数据链路为：

```
数据集快照（datasets.snapshot）
    │  采样 / 分发
    ▼
评测任务（eval_tasks，携带 fingerprint 指纹）
    │  推理引擎执行（vllm / trtllm / api）
    ▼
六能力域得分（eval_results.score_*）
    │  加权聚合（0.30推理+0.20语言+0.15对齐+0.15长文+0.10多模态+0.10业务）
    ▼
综合评分（eval_results.composite_score）
    │  Pareto 前沿计算
    ▼
评分—成本图谱气泡与性价比排名（前端可视化消费端）
```

该链路中的每一环都精确对应血缘三要素：**节点**为数据集快照、任务、域得分、综合评分、图谱点位；**边**为采样、推理、加权聚合、Pareto 计算四次派生；**变换逻辑**则被显式记录而非隐含。

### （二）平台的血缘实践亮点

1. **快照级溯源锚点**——`datasets.snapshot` 字段（如 `mmlu-pro@2026.08:snapshot-101`）将数据源头固化到不可变快照，杜绝了"数据集悄然更新导致评分漂移却无法解释"的血缘断链问题；
2. **任务指纹（fingerprint）即变换血缘**——每个评测任务的 `fingerprint` JSON 完整记录了模型版本（`model: gpt-5.2@5.2`）、数据快照清单、推理引擎版本（`engine: api@0.6`）与超参数（temperature、max_tokens），相当于把"这份得分是怎么算出来的"这一血缘信息作为一等公民持久化，任何评分均可完整重放与复现；
3. **聚合逻辑显式化**——六能力域到综合评分的加权公式在服务端固化并公开，血缘的"边"不是黑盒，而是可审计的确定函数；
4. **血缘断点续传**——任务状态机与断点续跑机制保证长周期评测中血缘链不因服务重启而断裂，进度落库即血缘中间态落库。

### （三）尚存提升空间

对照完整的数据血缘体系，平台仍有可演进方向：

1. **行级血缘缺失**——当前血缘粒度到"任务级"，单条评测样本（哪一道题、哪一次推理）尚未纳入追溯，后续可引入样本级 trace 记录；
2. **影响分析未产品化**——当某数据集快照升级（如 mmlu-pro 从 2026.08 升级至 2026.09）时，平台尚无自动圈定"哪些历史评分将不可比"的影响分析能力，可基于 snapshot 与 fingerprint 字段构建比对该能力；
3. **跨任务血缘图未可视化**——评分图谱呈现的是"评分×成本"分析视角，若叠加"模型—任务—数据集"血缘拓扑视图，将进一步提升结果可解释性。

### （四）小结

ID-009 平台虽未以"数据血缘"为名进行设计，但其"快照锚定 + 任务指纹 + 显式聚合 + 状态持久化"的架构实践，实质上已在评测域内落地了一套**轻量级、高可信的数据血缘机制**——每一份呈现在评分图谱上的气泡，都可以向上完整回答"数据从哪里来、经过什么计算、为何是这个数值"。这正是数据血缘"让数据可解释、可审计、可复现"核心价值的直接体现，也为平台后续接入真实评测引擎后的评分公信力奠定了工程基础。
